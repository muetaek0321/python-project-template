# Technical Debt Audit

## 1. 目的

プロジェクト内の技術的負債を発見し、保守性、変更容易性、信頼性、安全性、開発効率に与える影響を評価する。

単なるコーディングスタイルの指摘ではなく、将来的な変更コストや不具合リスクにつながる問題を優先的に検出する。

本スキルは調査とレポート作成のみを行う。ソースコードの修正、リファクタリング、設定変更は実施しない。

調査結果はMarkdownファイルとして、プロジェクトルート直下の `technical_debt_report.md` に出力する。あわせて会話内でも調査完了の報告とともにサマリーや推奨アクションを提示する。

## 2. 基本原則

- 実際のコード、設定、テスト、依存関係を根拠に判断する。
- 問題の場所、根拠、影響、改善案を具体的に示す。
- 推測と確認済みの事実を区別する。
- コーディングスタイルの好みだけを理由に負債と判定しない。
- プロジェクト固有の規約や設計方針を優先する。
- 既存の動作仕様を把握せずに、設計上の選択を誤りと断定しない。
- 同一原因による重複指摘を統合する。
- 問題が見つからないカテゴリについて、問題が存在しないと断定せず、調査範囲を明記する。
- 重要度、確信度、修正コストを分けて評価する。
- 判断材料が不足する場合は、要確認事項として報告する。
- 静的解析ツールの結果を活用するが、警告の存在だけで技術的負債と断定しない。
- 指定範囲を優先し、関連箇所を確認する必要がある場合のみ調査範囲を限定的に拡張する。
- 過去の調査結果との比較を前提とせず、毎回独立した監査として実施する。

## 3. 読み取り専用の制約

### 3.1 許可する操作

- ソースコード、テスト、設定ファイル、ドキュメントの読み取り
- ファイル構成、参照関係、依存関係の確認
- Gitの履歴や差分の参照
- 利用可能な静的解析ツールの実行
- 既存環境を利用したテストや依存関係チェック
- レポートファイル `technical_debt_report.md` の作成・更新
- 調査結果サマリーの会話内での提示

### 3.2 禁止する操作

- ソースコード、テスト、設定ファイルの編集
- 自動修正、フォーマット、リファクタリング（例: `uv run ruff format`, `uv run ruff check --fix` など）
- パッケージのインストール、更新、削除（例: `uv add`, `uv remove`, `pip install` など）
- ロックファイルや仮想環境の変更・再生成（例: `uv sync`, `uv lock` など）
- データベースや外部サービスへの書き込み
- Gitのコミット、ブランチ変更、リセット、チェックアウト
- 調査対象プロジェクトの設定変更
- レポートファイル（`technical_debt_report.md`）以外のファイルの新規作成・編集・削除
- 調査のためだけに実行する、動作や副作用が未確認のスクリプト

コマンドを実行する場合は、実行対象、必要な権限、副作用を確認する。

ファイルやキャッシュの生成、データの変更、外部通信などが発生する可能性がある操作は避ける。読み取り専用で実行できることを確認できない場合は、コマンドの実行を見送り、静的なコード調査で代替する。

テストやアプリケーションのコードを実行する場合も、データベース更新、ファイル書き込み、外部API呼び出しなどの可能性を考慮する。

既存の環境で安全に検証できない場合は、無理に実行せず、その制約をレポートに記載する。

## 4. 調査対象

プロジェクトの実際の構成に応じて、以下を調査する。

### 4.1 設計と責務分離

- 単一のクラスや関数への責務の集中
- 不必要に複雑なモジュール構成
- 循環依存や過剰な結合
- 抽象化の不足、または過剰な抽象化
- 不明瞭な依存関係や副作用
- 変更時に広範囲の修正を必要とする構造

### 4.2 可読性と保守性

- 過度に深いネストや複雑な条件分岐
- 不明瞭な命名や暗黙的な前提
- 過度に長い関数や巨大なクラス
- マジックナンバーや重複した定数
- 不要な複雑化や理解しにくい制御フロー

行数や命名だけを理由に問題と判定せず、実際の理解・変更コストを評価する。

### 4.3 重複と冗長性

- 複数箇所に存在する同一または類似の処理
- 重複する入力検証やエラー処理
- 同一設定値の不必要な多重定義
- 未使用コード、到達不能コード、不要な分岐
- 同じ機能を実現する複数の実装

重複を統合することで結合度が上がる場合など、共通化による副作用も考慮する。

### 4.4 エラー処理とリソース管理

- 例外の握りつぶし
- 不適切に広い例外捕捉
- エラー情報や原因の欠落
- 不明瞭な失敗時の挙動
- ファイル、接続、ロックなどの解放漏れ
- リトライやタイムアウトの不適切な設計

例外捕捉の広さだけでは判断せず、処理の目的とエラー回復方針を確認する。

### 4.5 型とデータ設計

- 型情報の不足による理解・検証の困難さ
- Anyや型抑制の過剰な利用
- 不整合なデータ構造
- 不必要な型変換や重複した変換処理
- 型定義と実際の値の扱いの不一致
- Pydanticなどによる入力検証の不整合

型注釈や特定ライブラリの利用自体を必須条件にはしない。

### 4.6 テスト品質

- 重要な業務ロジックに対するテスト不足
- 境界値や異常系の検証不足
- 外部依存を含む処理の検証不足
- テストの重複や過度な複雑化
- 実行順序や環境に依存する不安定なテスト
- 実装詳細に過度に依存したテスト
- テスト容易性を損なう設計

カバレッジの数値だけでテスト品質を判定しない。重要な処理とリスクに対する検証の有無を重視する。

### 4.7 依存関係と開発環境（uv・pyproject.toml）

- `uv.lock` と `pyproject.toml`（`dependencies`, `dependency-groups`）の乖離や未同期
- `.python-version` と `pyproject.toml` の `requires-python` の不一致
- 不要または重複する依存パッケージ（開発用依存と本番用依存の混在など）
- バージョン制約の不整合や過度に緩い/厳しい指定
- `[tool.uv]` 設定の過不足や不整合
- 循環依存や依存関係の過剰な結合
- 非推奨APIや廃止済みAPIの利用
- 再現可能な環境構築を妨げる設定

本プロジェクトの標準ツールである `uv` および `pyproject.toml` の定義内容を確認してから評価する。

### 4.8 設定と構成

- 同一設定の重複管理
- 環境依存値の不適切なハードコード
- 設定値と実装の不一致
- 環境変数や秘密情報の不適切な取り扱い
- 設定変更時の影響範囲が広すぎる構造

### 4.9 セキュリティと信頼性

- 外部入力の検証不足
- 秘密情報や認証情報のハードコード
- 危険なデシリアライズやコマンド実行
- パストラバーサルや不適切なファイル操作
- 認証・認可の検証漏れ
- 不適切なログ出力による情報漏えい

脆弱性の可能性がある場合は、具体的な根拠と条件を示す。確認できていない攻撃可能性を断定しない。

### 4.10 パフォーマンス

- 不要な反復処理や重複計算
- 非効率なデータアクセス
- 大量データに対する不適切な処理
- 不必要なオブジェクト生成やコピー
- キャッシュやバッチ処理の検討が必要な箇所

計測値がない場合は、確認済みの性能問題と断定せず、コード構造から推測されるリスクとして報告する。

## 5. 調査範囲の決定

### 5.1 ユーザーが対象を指定した場合

指定されたディレクトリ、ファイル、モジュールを優先して調査する。

対象範囲を明確にし、指定された範囲を超えて無制限に調査しない。

問題の原因や影響を判断するために必要な場合は、以下の関連箇所を追加で確認する。

- 対象関数やクラスの呼び出し元
- 対象モジュールから参照される内部モジュール
- 関連するテストコード
- 関連する設定ファイル
- 関連する依存関係の定義

追加調査は指摘の検証に必要な範囲に限定し、レポートに明記する。

### 5.2 ユーザーが対象を指定しない場合

プロジェクト全体の構成を確認し、主要なアプリケーションコードを中心に調査する。

最初に調査対象と除外対象を決め、調査範囲をレポートに記載する。

プロジェクトが大規模な場合は、すべてのファイルを確認したかのように報告せず、調査済み範囲と未調査範囲を明示する。

### 5.3 通常の除外対象

以下は原則として除外する。ただし、ユーザーが明示的に指定した場合や、問題の検証に必要な場合は、必要な範囲を確認する。

- 仮想環境（`.venv/` 等）
- ツールキャッシュ（`.ruff_cache/`, `.pytest_cache/`, `.mypy_cache/`, `__pycache__/` 等）
- ビルド生成物（`dist/`, `build/`, `*.egg-info/` 等）
- 外部ライブラリのソースコード
- 自動生成コード
- 大容量のデータファイル
- 監査対象と無関係なファイル

除外した領域に重大な問題が存在しないと断定しない。

## 6. 静的解析ツールの活用

### 6.1 基本方針

プロジェクトの仮想環境に導入されている静的解析ツールを調査に活用する。

本プロジェクトではパッケージ管理に `uv` を使用しているため、**コマンドの実行は必ず `uv run` を経由する**（例: `uv run <command>`）。直接システムグローバルのコマンドを実行したり、仮想環境をバイパスして実行してはならない。

ツールを利用する前に、以下を確認する。

- ツールが `pyproject.toml` や現在の仮想環境で既に利用可能か
- プロジェクトで使用されている設定（`[tool.ruff]`, `[tool.pytest.ini_options]` 等）があるか
- 指定された調査範囲に適用できるか
- 実行によってファイルや環境が変更されないか
- 実行に必要な外部通信や追加権限がないか

新規ツールの導入（`uv add` 等）や設定変更は行わない。

### 6.2 推奨コマンド例（読み取り専用）

プロジェクトの構成と環境に応じて、副作用のない以下のコマンドを検討する。

- **Ruff（静的リント）**:
  `uv run ruff check --no-fix .`
  （※コード変更を防止するため `--no-fix` を明示する）
- **依存関係とロックファイルの検証**:
  `uv lock --check`（`pyproject.toml` と `uv.lock` の同期確認）
  `uv pip check`（インストール済みパッケージの競合・依存不整合確認）
- **型チェック（設定されている場合）**:
  `uv run mypy .` または `uv run pyright`
- **テストの検証**:
  `uv run pytest --collect-only`（テストの定義一覧・構文収集のみ。実行副作用なし）
  `uv run pytest`（※副作用がないことが確認できている場合のみ実行）

これらは候補であり、すべてのツールの実行を必須としない。環境で安全に実行できるものを優先する。

### 6.3 実行時の注意

- 自動修正オプション（`--fix`）を指定しない。
- フォーマット（`uv run ruff format` 等）やコード変更を伴うコマンドを実行しない。
- 環境変更コマンド（`uv add`, `uv remove`, `uv sync` 等）を実行しない。
- テスト実行時のデータベース更新、ファイル書き込み、外部通信に注意する。
- キャッシュやレポートなどのファイルが生成される可能性がある場合は実行を避ける。
- 安全性を確認できない場合は、コマンドを実行せず静的なコード調査を行う。
- 実行結果、終了コード、警告、実行できなかった理由を正確に記録する。

### 6.4 結果の解釈

ツールの警告やエラーをそのまま技術的負債として登録しない。

コード、設定、プロジェクトの規約と照合し、実際の影響を確認する。

ツールを実行できなかった場合、未実行であることを明示する。実行していない検査を実施済みとして報告しない。

## 7. 指摘の検証と評価

### 7.1 指摘の検証

各候補について、以下を確認する。

- 問題を示す具体的な根拠が存在するか
- プロジェクトの仕様や規約で正当化されないか
- 影響を受ける処理や利用箇所を確認できるか
- 既存の指摘と同じ原因ではないか
- 改善案が新たな複雑性や結合を生まないか
- 対象範囲外の情報に依存していないか

根拠が不足する場合は、確定的な指摘ではなく要確認事項として扱う。

### 7.2 重要度

- Critical: 重大なセキュリティ侵害、データ損失、深刻な障害につながる具体的な問題。
- High: 主要機能の信頼性や保守性に大きな影響を与える問題。
- Medium: 将来の変更コストや不具合リスクを継続的に増加させる問題。
- Low: 影響が限定的で、小規模な改善によって解消できる問題。

単純な行数や指摘数ではなく、実際の影響、発生可能性、対象機能の重要性を考慮する。

### 7.3 確信度

- High: コードや設定から問題を直接確認できる。
- Medium: 問題の兆候は確認できるが、実行時の挙動などが未確認。
- Low: 推測の要素が大きく、追加調査が必要。

### 7.4 修正コスト

- Small: 限定的な変更で解消できる見込みがある。
- Medium: 複数箇所の変更やテストの追加が必要な見込みがある。
- Large: アーキテクチャや複数モジュールにまたがる変更が必要な見込みがある。

修正コストは調査時点の推定値であり、実装前に再評価が必要な場合がある。

## 8. レポートの出力形式

調査結果はMarkdown形式でファイルに出力する。出力先ファイル名は `technical_debt_report.md`（原則としてプロジェクトルート直下）とする。

レポートファイルの作成完了後、会話内にも完了報告とともにサマリーや優先度の高い推奨アクションを提示し、詳細な内容は `technical_debt_report.md` を参照できるように案内する。

`technical_debt_report.md` に記載する内容は以下の構成とする。

### 8.1 サマリー

以下を記載する。

- 調査対象
- 調査範囲と除外範囲
- 調査方法と利用したツール
- 主な発見事項
- 優先して対処すべき問題
- 調査上の制約

件数を集計する場合は、確定した指摘と要確認事項を分ける。

### 8.2 負債一覧

各指摘について、以下の情報を記載する。

- ID: TD-001などの識別子
- タイトル: 問題を簡潔に表す名称
- 分類: 該当する検出カテゴリ
- 重要度: Critical / High / Medium / Low
- 確信度: High / Medium / Low
- 対象箇所: ファイルパスと確認できた行番号
- 根拠: 実際に確認したコードや設定上の問題
- 影響: 保守性、信頼性、安全性、開発効率などへの影響
- 改善案: 実装方針や改善の方向性
- 修正コスト: Small / Medium / Large
- 補足: 未確認事項や判断の前提

行番号は実際のファイルを確認して特定する。正確な行番号を確認できない場合は、ファイル名と関数名などで位置を示す。

### 8.3 推奨アクション

指摘の一覧とは別に、次の観点で改善の順序を提案する。

1. 重大なセキュリティ・信頼性リスク
2. 主要機能の変更を妨げる構造上の問題
3. 重複や複雑性による継続的な保守コスト
4. テスト品質や開発環境の改善
5. 影響が限定的な小規模改善

同じ重要度の場合は、影響範囲、再発リスク、修正コストを考慮して順序を決める。

### 8.4 要確認事項

コードからは断定できない問題、実行環境がないため検証できない問題、仕様や運用情報が不足している問題を列挙する。

### 8.5 調査範囲と制約

確認したディレクトリ、利用したツール、実行できなかった検証、除外した領域を明記する。

指定された範囲外のコードを確認した場合は、その理由も記載する。

## 9. 出力上の注意

- 調査レポートは完全な内容を `technical_debt_report.md` にMarkdown形式で書き出す。
- 重要度の高い指摘から順に出力する。
- 1つの問題を複数の指摘に分割しすぎない。
- 改善案は問題の根拠と対応するように記述する。
- 不必要に大規模なリファクタリングを提案しない。
- 確認できないテスト結果やツールの実行結果を捏造しない。
- 負債が見つからなかった場合も、調査範囲と限界を明示する。
- 過去のレポートとの比較は必須としない。
- コードの変更は行わず、ユーザーが次の対応を判断できる情報を提供する。
- 会話内ではレポート作成完了を報告し、サマリーや最優先の推奨アクションを抜粋して案内する。

## 10. 呼び出し例

ユーザーが以下のように要求した際に本スキルを起動します：

- `技術的負債を調査して`
- `このプロジェクトのコード品質や負債を監査して`
- `src/ 配下の保守性・設計上の課題をレポートして`
- `依存関係や設定、テストに問題がないかレビューして`
- `リファクタリングすべき箇所の優先順位を分析して`
